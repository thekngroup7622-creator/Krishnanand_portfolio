1.1
Objective & Scope of Training
The primary objective of this manual is to train new employees and trainees to independently create
professional, high-impact cricket visual analytics for various use cases, including pre-match
preparation, post-match analysis, and ad-hoc statistical inquiries.
Scope of This Program
This training program covers the following areas in detail:
• Statistical Thinking: Developing foundational knowledge in cricket metric definitions, data
interpretation, and contextual analysis.
• Data Sourcing & Wrangling: Mastering data collection from multiple platforms and
engineering derived KPIs in Google Sheets.
• Tool Architecture: Training on the Python tool's source code, modules, dependencies, and
configuration.
• Template Mastery: Enabling trainees to modify existing templates and create new ones
independently.
• Requirement Translation: Converting analytics requirements into data selection, calculation
logic, and appropriate visuals.
• Quality Assurance: Ensuring trainees can troubleshoot code, handle data quality issues, and
validate outputs.
• Assessment: Final competency evaluation and reporting on performance gaps.
End-to-End Workflow
Every analytical visual produced by this team — regardless of chart type, use case, or complexity —
follows the same three-step workflow. All sections of this manual are anchored to one of these steps:

STEP 02
Data Wrangling

1.2
The Analytical Mindset: Cricket
Statistical Thinking
Effective cricket analytics requires more than just processing numbers — it requires a deep
understanding of the game's dynamics and the ability to translate raw data into actionable insight.
Skill What It Means in Practice Example
Identify the core
question
Is this for a tactical pre-match
plan or a post-match review?
The chart type, data scope, and
takeaway all change.
"Where does this batter score?" vs. "What went
wrong in the powerplay?"
Select the right
data
Distinguish between aggregate
stats and context-dependent
data. Never mix scopes or time
windows.
Career data is wrong for a single-innings chart;
venue-filtered data is wrong for a career profile.
Interpret trends A 'high strike rate' means
different things in different
contexts.
SR 150 in death overs is expected; SR 150 in a
Test first session is extraordinary.
Synthesize
insights
Move beyond raw data — a
number without a 'so what' is not
analysis.
"SR dropped 40%% in middle overs" → "Rotate
strike better against spin in overs 7-15."
TIP: The 3-Second Test
Before sharing any chart, ask: can a coach understand the key insight within 3 seconds of looking at it? If
not, the chart needs simplification, better annotation, or a different type altogether.

1.3
Branding & Aesthetic Guidelines
All visualizations must strictly adhere to CricRadio's brand identity. Consistency across every
deliverable builds credibility and ensures outputs are instantly recognizable.
Theme Palette
Color Hex Code Usage
Navy Blue #001D38 Primary text, axis labels, titles, critical data points, primary chart
fills
Sky Blue #69A7EF Secondary highlights, accent bars, data series indicators, callout
elements
Off-White #FAF9F6 Base background for all charts, slide decks, and report pages
Application Rules
• Use Navy (#001D38) for primary axis labels, titles, and critical data points.
• Use Sky Blue (#69A7EF) for secondary highlights, bars, or data series indicators.
• Use Off-White (#FAF9F6) as the base background color for all charts and slide decks.
• Ensure high contrast between text and background to maintain readability on screens and
projectors.
• All chart footers must include: "Source: CricRadio Data Portal | [Date]"
IMPORTANT: No Default Colors
Never use default tool/library colors in any published chart. Every visual must use the CricRadio brand
palette. This applies to AI-generated output as well — always specify brand colors in your prompts.

2.2
Data Wrangling in Google Sheets:
Defining Unique KPIs
Moving beyond basic stats, trainees will learn to engineer unique performance indicators critical for
modern cricket analysis. This is where raw data becomes meaningful.
KPI Relationship Map
Understanding how KPIs relate to each other prevents calculation errors and ensures consistency:
Total Runs Scored
(Primary Input)
Boundary Runs % Activity Runs %
Boundary Rate Dots % / Dots Rate
Boundary Runs % + Activity Runs % = 100%
Wrangling Workflow
1. Export raw data from your source platform as CSV.
2. Import into Google Sheets — clean column headers, check for missing/duplicate rows.
3. Engineer KPIs using the formulas in Section 2.5. Use consistent column naming.
4. Apply thresholds — exclude low sample sizes (e.g., use AVERAGE(Balls Faced) as
minimum).
5. Validate — spot-check at least one row with a manual calculation before proceeding.
TIP: Consistency First
Always name new KPIs consistently with the existing glossary before introducing them into a visual. This
keeps templates reusable across trainees and projects.

Prompt Engineering Best Practices
A good chart-generation prompt gives the AI tool everything a human designer would need: the data,
the question, the constraints, and the brand identity.
• State the question, not just the chart type — "show where this batter scores" produces a
better result than "make a pie chart."

2.5
Hands-on Implementation of Derived
KPIs
This section details the specific calculations required to derive advanced cricket KPIs from raw data.
Mastering these formulas ensures consistency across all analytical visualizations.
KPI Formula What It Measures
Boundary
Runs %
(Total Runs from Boundaries / Total
Runs Scored) x 100
A player's reliance on boundaries for scoring —
high values indicate power-dependent batting
Boundary
Rate
Total Balls Faced / Total
Boundaries Hit
How frequently a player finds the boundary
(e.g., 4.5 = one boundary every 4.5 balls)
Dots % (Total Dot Balls / Total Balls Faced)
x 100
A player's ability to rotate strike — high values
indicate difficulty scoring against specific
bowling
Dots Rate Total Balls / Total Dots Granular scoring-to-non-scoring delivery ratio —
complements Dots % with a frequency view
Activity Runs
%
(Singles + Doubles + Triples / Total
Runs) x 100 Also: 100 - Boundary
Runs %
Efficiency in 'busy' batting and strike rotation —
inverse of boundary dependency
NOTE: Confirm Before Training Delivery
These definitions reflect standard convention. Confirm each against the internal tool's logic before using this
page in a live training session — internal tooling may use slightly different denominators.

Python Environment & Streamlit
Architecture
This section provides a complete technical walkthrough of the CricRadio Ball-by-Ball (BBB) Data
Portal — a Streamlit-based tool that pulls live match data from an external cricket API, processes it
into a clean analytical DataFrame with 38 derived columns, and exports it as a downloadable CSV.
This tool replaces manual scorecard scraping entirely. It automates data collection, normalisation,
and derived-metric computation in a single click — producing the raw datasets that feed into the
visualizations covered in Section 2.
System Architecture Overview
The codebase is organized into 6 distinct layers, each with a clear responsibility. Understanding this
architecture is essential before modifying any part of the tool.
Layer 01
Configuration Layer Series config, API URL, headers, session
Layer 02
Data Ingestion Layer API endpoints, concurrent fetching, caching
Layer 03
Normalisation Engine 6 lookup maps, LRU-cached normalisation
Layer 04
Data Processing Layer Ball extraction, derived columns, style inference
Layer 05
Output Layer 38-column final DataFrame, rename & export
Layer 06
UI Layer Streamlit app, sidebar, match selector, download

API Data Flow & Endpoints
The tool hits 3 distinct API endpoints per match extraction. Understanding this flow is essential for
debugging data issues and for knowing where a missing field originates.
Endpoint 1
/fixtures/yearfilter
→ Completed match list (paginated)
Endpoint 2
/views/scorecard
→ Player map, team map, match metadata
Endpoint 3
/views/comments
→ Ball-by-ball data (1 call per innings, up to 4)
Endpoints 2 + 3 are fetched concurrently via ThreadPoolExecutor
All results cached with @st.cache_data(ttl=1800) = 30-minute TTL
The isCompleted Parameter
f"&isCompleted;=false" # false = for ongoing live games # true = for completed games
This query parameter in fetch_completed_fixtures() controls whether the API returns
live/in-progress matches or completed matches. Change this value based on whether you need to
extract data from a match that is still being played (false) or one that has finished (true).
NOTE: Pagination & Deduplication
The fixture list is paginated (50 per page, up to 20 pages). The function automatically deduplicates fixtures
by ID and sorts them by start date. A 0.2-second sleep is inserted between API pages to avoid rate limiting.

Bowler Style Inference Logic
The build_bowler_style_map() function infers each bowler's style (Fast, Medium, OffSpin,
Orthodox, LegSpin, Chinaman) by analyzing the set of delivery types they've bowled across all their
deliveries.

by Bowler X
Count: Pace vs Spin
deliveries in each group
Assigned Style
"Fast" / "OffSpin" / etc
Rules:
• If spin deliveries > pace deliveries → spin category (OffSpin / Orthodox / LegSpin based on hand)
• If pace deliveries > 0 and seam variants present → Fast; otherwise → Medium
• Left-arm spinners default to "Orthodox"; right-arm spinners to "OffSpin"

AI-Assisted Code Generation in Colab
Google Colab's built-in AI assistant accelerates the wrangling process. Here's how to use it effectively
for cricket analytics KPI computation:
Effective Prompting for Colab AI
• Be specific about column names: Reference the exact column names from the BBB export
(e.g., "using the 'Batter Runs' column" not "using the runs data").
• State the grouping clearly: "Group by Innings and Striker" or "Group by Bowler" — Colab AI
needs to know the aggregation level.
• Describe the output shape: "Return a DataFrame with one row per batter, columns for each
KPI" — define the expected result.
• Request validation: "Also print the top 5 rows sorted by Boundary Rate to verify" — always
ask for a sanity check.
• Handle edge cases: "If a batter has faced fewer than 10 balls, exclude them from the
calculation" — set thresholds explicitly.
Example AI Prompt for Colab
"Using the loaded DataFrame `df`, calculate the following KPIs per batter per innings: 1.
Boundary Runs % = (runs from 4s and 6s / total batter runs) * 100 2. Dots % = (balls where
Runs==0 and Wides==0 and No Balls==0) / total legal balls * 100 3. False Shots % = (sum of
False Shot column / total legal balls) * 100 Group by: Innings, Striker columns. Exclude
batters who faced fewer than 10 legal deliveries. Output: A clean summary DataFrame sorted by
Boundary Runs % descending. Print the first 10 rows to verify."
TIP: Review Before Proceeding
Always review AI-generated code for correctness before using its output in a visualization. Common AI
mistakes include: wrong groupby columns, not filtering out extras (wides/no-balls) from ball counts, and
dividing by zero when a batter has scored 0 runs. Add .replace(0, np.nan) before any division to handle edge
cases.

Case Study Structure for Advanced Visuals
Each advanced visualization case study follows a consistent 3-phase structure built on top of the

Phase 1 — Data Structuring
In this phase, the wrangled dataset from Colab is filtered and grouped by the relevant analytical
dimension. For example, to build a Pitching Length breakdown:
• Filter the DataFrame to the target player/team and innings scope.
• Group by the Pitching Length column (Full Toss, Yorker, Half Volley, Length Delivery, Back of
Length, Short Length).
• Aggregate: count balls, sum runs, count boundaries, count dot balls, sum false shots per
group.
Phase 2 — KPI Computation
Using the grouped aggregates, compute the derived KPIs from Section 3.2 within each group:
• Calculate Boundary Runs %, Dots %, Activity Runs %, False Shots % per Pitching Length
category.
• Calculate Boundary Rate, Dots Rate, False Shot Induced Rate per category.
• Add Strike Rate and sample size (balls faced) per category for context.
• Output a clean, one-row-per-category summary table ready for the visualization prompt.
Phase 3 — AI-Powered Visualization
The structured summary table is then used to generate broadcast-quality visuals using AI tools. The
key differentiator in this phase is the use of reference formats from the official GitHub repository and
structured prompting frameworks.
• Reference formats: Pre-approved visual templates stored in the GitHub repository that define
the expected look, layout, color scheme, and annotation style for each dimension breakdown.
• Structured prompting: The AI prompt includes the data table, the reference image/format, the
brand specifications, and strict constraints — all in a single, reproducible prompt.
• Consistency: Using reference formats ensures that every advanced visual produced by any
trainee matches the team's established design language.
